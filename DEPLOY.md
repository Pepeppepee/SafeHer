# Deploying SafeHer to Render (free tier)

The whole deployment is described by [render.yaml](render.yaml), so you point Render at
the repo once and it creates both the web service and the database.

## What "free" costs you

Two limits are worth knowing before you send the link to anyone:

- **The service sleeps after ~15 minutes of inactivity.** The next visitor waits roughly
  30-60 seconds while it wakes up. Fine for showing the app to people; not what you want
  for someone opening it while she's actually out. Upgrading the service to a paid plan
  removes this.
- **Free Postgres is temporary.** Render removes free databases after about a month, so
  treat everything in it as disposable until the database is on a paid plan.

The app itself is production-configured either way — `DEBUG` is off, the secret key is
generated by Render, and HTTPS is enforced.

## First deploy

1. **Push to GitHub.** Render deploys from a repository, so the code has to be there:

   ```bash
   git add -A
   git commit -m "Add Render deployment config"
   git push
   ```

2. **Create the blueprint.** In Render: **New > Blueprint**, pick this repo, and apply.
   It reads `render.yaml` and creates the `safeher` web service plus the `safeher-db`
   Postgres database, with `DATABASE_URL` and a generated `DJANGO_SECRET_KEY` already
   wired in. Nothing to fill in by hand.

3. **Wait for the build.** The first one takes a few minutes. `build.sh` installs
   dependencies, collects static files, runs migrations, and seeds the 48 valley places.
   When it finishes you get a URL like `https://safeher.onrender.com`.

4. **Create your admin account.** Free instances have no shell, so this happens through
   environment variables. In the service's **Environment** tab add:

   | Key | Value |
   | --- | --- |
   | `DJANGO_SUPERUSER_PHONE` | your phone number, e.g. `9800000000` |
   | `DJANGO_SUPERUSER_PASSWORD` | a strong password |
   | `DJANGO_SUPERUSER_FIRST_NAME` | your name |

   Saving triggers a redeploy that creates the account. **Then delete
   `DJANGO_SUPERUSER_PASSWORD`** — it has done its job and shouldn't sit in the
   dashboard. Later deploys log "That phone is already taken" and carry on, which is
   expected.

5. **Log in at `/admin/`** and create invite codes — signup is invite-only, so without
   at least one code nobody can register.

## Pointing the mobile app at it

`mobile/src/api.js` now reads `EXPO_PUBLIC_API_BASE`, so no code edit is needed. Create
`mobile/.env`:

```
EXPO_PUBLIC_API_BASE=https://safeher.onrender.com
```

Expo inlines `EXPO_PUBLIC_*` variables at build time, so restart the dev server (or
rebuild) after changing it. With nothing set it falls back to the old ngrok tunnel.

## Everyday deploys

Push to the default branch. Render rebuilds and restarts automatically — migrations and
seeding run every time as part of `build.sh`, and the seed is idempotent, so re-running
it refreshes the valley data rather than duplicating it.

## Local development

Unchanged apart from one new step — settings now come from the environment:

```bash
cp .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(64))"   # paste into DJANGO_SECRET_KEY
pip install -r requirements.txt
python manage.py migrate
python manage.py seed_valley_places
python manage.py runserver
```

With `DJANGO_DEBUG=1` and no `DATABASE_URL`, it uses `db.sqlite3` exactly as before.

## If something goes wrong

**Build fails on the Python version.** `render.yaml` asks for `PYTHON_VERSION: "3.13"`
because Django 6.1 needs 3.12 or newer. If Render rejects the short form, set it to a
full version such as `3.13.4` in the Environment tab.

**`DisallowedHost` errors.** Custom domains need to be listed. Add
`DJANGO_ALLOWED_HOSTS=yourdomain.com` — the `*.onrender.com` URL already works, and CSRF
trusted origins are derived from that variable automatically.

**`ImproperlyConfigured: DJANGO_SECRET_KEY is not set`.** Expected if you run the app
outside Render without a `.env`. The settings fail closed on purpose rather than starting
with an insecure default.

**Static files or admin CSS missing.** `collectstatic` runs in `build.sh` and WhiteNoise
serves the result; check the build log for a `collectstatic` error.

## Moving off the free tier later

Upgrade the service plan to stop the sleeping, and the database plan to make it permanent.
Neither requires a code change. Once you're on a custom domain and happy with it, set
`DJANGO_HSTS_SECONDS=2592000` to turn on HSTS — it's deliberately off for now because
it's a browser-cached promise that's awkward to undo.
